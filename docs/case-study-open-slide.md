# Case study: porting Open Slide

What upstream does, what this host forbids, what we did instead, and what it
cost. Written from one port; every failure listed was hit, not predicted.

Upstream: [1weiho/open-slide](https://github.com/1weiho/open-slide) @
`663c957`, 28k lines. A Vite app whose **dev server is the product** — it
compiles each `slides/<id>/index.tsx` on demand, serves a `/__*` HTTP API for
editing, and gates the entire authoring UI behind `import.meta.env.DEV`.

## Two attempts

| | Re-implementation (#7) | Port (#9) |
| --- | --- | --- |
| Source | 2.8k lines, written fresh | ~21.7k vendored unmodified |
| Verbatim overlap with upstream | ~3.5% (97 lines) | ~100% of the app layer |
| A slide is | a JSON document of typed blocks | a React module, as upstream |
| Authoring | block form | upstream's own editor + inspector |
| Validated | fully, on a live host | compiles + renders; not yet validated |

The first shipped quickly and passed every check. It is also, side by side with
the reference build, visibly a different app. Both are kept: the lesson is that
"find the app inside the framework" (Phase 0) legitimately produces a *new
app*, and calling that a port misleads the human validator.

## The seams

Only two boundaries assume a dev server. Everything between them is untouched,
which is the whole trick: the port cannot drift from upstream where it does not
have to.

| Upstream mechanism | Host constraint | What we did | Trade-off |
| --- | --- | --- | --- |
| `virtual:open-slide/slides` — Vite globs slides, emits `import()` per slide | one fixed entry, esbuild, no per-content compile step | read source from `fs`, transform TSX with Sucrase, evaluate with `new Function` | slides compile per session, not per build; a bad slide is now a *runtime* error, so it must be surfaced (see Issue 7) |
| `virtual:open-slide/{config,folders,themes}` | no build-time codegen | ordinary modules, same contracts, mapped by `tsconfig` `paths` | none — **no vendored import statement changed** |
| `/__edit`, `/__slides`, `/__folders`, `/__notes`, `/__design`, `/__assets`, `/__comments` | no server in a sealed iframe | patch `fetch` before mount; answer in-process from project storage, same wire shapes | vendored UI stays byte-identical; gaps must return honest `501`s, never a fake `200` |
| `BrowserRouter` | `project://<id>/` has no server to answer a pushed path | `HashRouter` | one-line edit; URLs differ from upstream |
| `import.meta.env.DEV` gating all authoring | esbuild ESM **with code splitting** → `import.meta` is per-chunk, unpatchable from the entry | mechanical rewrite to `__OSD_ENV__`, published by a first-imported module | 56 references across 21 files; re-vendoring upstream needs the codemod re-run |

**`DEV` is deliberately `true`.** Upstream's production build is a viewer; the
app worth porting is the dev-mode one.

## Issues hit, in order

1. **`.download` assignment** (`lib/dom.ts`) — hard build error, spec §25.
   Rerouted through `files.save`, whose picker is its own consent surface, so
   the permission envelope stays `fs` + `ui.notify`.
2. **The host installs no npm dependencies.** It builds against its own palette
   (React, ReactDOM, SDK). A bare `import 'cmdk'` resolves *only* because the
   host's own `node_modules` leak in through esbuild `nodePaths` — at the
   host's version, not yours. Versions already disagreed: `tailwind-merge`
   3.5 vs 3.6, `fflate` 0.4 vs 0.8, `lucide-react` 1.21 vs 1.25.
   **Fix: vendor everything.** 37 entry points pre-bundled into `vendor/dist`
   and mapped by `tsconfig` `paths`; regenerated by `vendor/build-vendor.mjs`
   from the pinned lockfile. Proof: the app builds with `node_modules` deleted
   and no host paths on the resolve chain.
3. **Deep subpath imports** — `@base-ui/react/tooltip` and 15 siblings each
   need their own vendored entry; a single package-level bundle is not enough.
4. **`Dynamic require of "react" is not supported`** — CJS deps
   (`use-sync-external-store`, and the base-ui bundles that depend on it) call
   `require('react')`; with react marked external in an ESM bundle esbuild
   compiles that into a stub that throws. Fixed with a resolver plugin: react
   resolves to a real ESM shim *inside* vendored bundles, and only that shim's
   own import stays external — one React, no dynamic require. The CJS
   `useSyncExternalStore` backport was replaced by React's built-in.
5. **`config.locale` is a Locale table, not an id.** Shimming it as `'en'`
   crashed at `t.appTitle`. Contracts in `virtual.d.ts` are types, not shapes —
   read what the consumer actually indexes.
6. **Module-eval order beat the async warm-up.** `app/lib/slides.ts` snapshots
   `export const slideIds = ids` at module scope. Upstream can do that because
   Vite walked the directory at build time; here the list is async, and with a
   static import every vendored module body runs before the entry's first
   `await` — so the app mounted against an empty workspace. **Fix: import the
   app dynamically, after the warm-up.** This is the one that looks like a
   storage bug and is not.
7. **A runtime-compiled slide needs a visible failure path.** Upstream's
   compile errors surface in the dev server; here a throw inside `loadSlide`
   leaves a thumbnail spinning. Errors are logged and rethrown.
8. **Occluded window = no rendering steps.** With the host window not
   frontmost, `visibilityState` stays `hidden` and no `ResizeObserver`,
   `resize`, `rAF` or `IntersectionObserver` callback fires — lazy thumbnails
   never start and container-measuring code reads stale. Raise the window
   before concluding anything about layout or lazy loading.

## What worked best

- **Re-serving the API instead of rewriting its call sites.** Patching `fetch`
  kept ~20k lines byte-identical. Rewriting call sites would have been days of
  edits and permanent drift.
- **`tsconfig` `paths` as the seam.** Both virtual modules and vendored
  packages are redirected without touching a single import statement.
- **Vendoring every dependency.** Slower to set up, but the app now depends on
  nothing but itself, and host upgrades cannot silently break it.
- **Deleting `node_modules` and rebuilding** as the proof of self-containment.
  Nothing else actually demonstrates it.

## What we would do differently

- Check the palette *first*. The dependency question decides whether a port is
  hours or days, and it is answerable in one command.
- Read the consumers of every shimmed contract before writing the shim (issue
  5), and check for module-scope snapshots of async data (issue 6).

## Still open

Page reorder/delete/duplicate (needs `editing/slide-ops` moved off `node:fs`),
asset writes, splice edits — all return `501` rather than failing silently.
Presenter *window*, HTML/PDF/PPTX export, icon search and HMR are argued as
dropped in `open-slide/UPSTREAM.md`. React 19 against upstream's React 18 is
compile-clean but not yet exercised across the whole UI.
